# 桌面助手 · 语音 AI 功能设计（v1 草案）

> 状态：**设计阶段，未实现**
> 目标：用板载麦克风与喇叭，接入 DeepSeek，做一个能对话、能控制设备的语音助手

---

## 1. 体验定义

### 它应该是什么

一个**坐在桌上的小助手**，不是智能音箱：

- 你按一下它（或喊它），它**眼睛看向你**，然后开始听
- 你说完，它**眼睛转一下**表示在想
- 它回答时**嘴跟着声音动**
- 它能**顺手帮你操作自己**：「看看天气」→ 自动切到天气屏；「切换到表情」→ 切回脸

### 一条对话的时间预算（目标）

| 环节 | 目标 | 备注 |
|---|---|---|
| 端点检测（判定"说完了"）| 500 ms | 静音 700 ms 判定，可调 |
| 音频上传（3 秒 @16k/16bit = 96 KB）| 200–400 ms | 局域网 Wi-Fi |
| ASR | 500–1000 ms | 取决于用哪家 |
| DeepSeek 首 token | 400–800 ms | `stream=true` |
| TTS 首段音频 | 300–600 ms | 按句切分，第一句就发 |
| **首字出声** | **≈ 2.0–3.3 秒** | 可接受；按键说话省掉唤醒等待 |

> 关键：**服务端必须逐句流水线**，不能等整段回答生成完再合成语音，否则要 8–10 秒。

## 2. 核心约束：DeepSeek 不管语音

DeepSeek API 官方功能列表（实测确认）：

| 能力 | `deepseek-flash` | `deepseek-v4-pro` |
|---|---|---|
| Vision | ✅ | ❌ |
| Tool Calls | ✅ | ✅ |
| JSON Output | ✅ | ✅ |
| Thinking 模式 | ✅ | ✅ |
| **ASR / TTS / Realtime** | **❌ 完全没有** | **❌** |

上下文 1M，最大输出 384K，价格极低（cache miss 输入 $0.15/1M，输出 $0.6/1M，off-peak）。

**所以「语音→文字」和「文字→语音」必须另找方案。** 这是整个设计的分水岭。

## 3. 三条架构路线

### 路线 A：全部在设备上

- ASR：`esp-sr` 的 **MultiNet 只支持命令词**，不能自由说话。要自由对话得放个大模型，flash 装不下。
- TTS：`esp-tts` 中文机械音，约 1–2 MB flash。

**结论：❌** 体验差、flash 不够（当前只剩 1.9 MB）、且无法升级。

### 路线 B：设备直连多家云服务

设备里存 DeepSeek + ASR + TTS 三家的 key，自己做音频编解码和流式编排。

**结论：❌** 三把 key 全在设备上（我们之前为 admin key 纠结过，这里是三倍的问题）；设备代码复杂度暴涨；换个 ASR 供应商要重新烧固件。

### 路线 C：设备当"哑终端"，服务端编排 —— ✅ **推荐**

```
设备                                    服务端（你自己的机器）
────                                    ──────────────────────
拾音 → 16k PCM ─┐
                │  POST /voice (WAV)
                └──────────────────────────> ASR ──> DeepSeek(stream)
                                                       │ 逐句
   播放 <── PCM 流 ──────────────────────────── TTS <──┘
```

**为什么推荐：**

| 好处 | 说明 |
|---|---|
| key 全在服务端 | 设备 flash 被读走也没有任何凭据 |
| 设备代码简单 | 只做 I2S 收、I2S 发、HTTP |
| 随时换模型 | 换 ASR/TTS/提示词都不用重烧固件 |
| 可以用 Tool Calls | 服务端编排工具调用，设备只执行 |
| 已经有服务器 | 你的 `papaclaoud.top` 就是现成的 |

**代价**：依赖服务端在线。断网时降级为「无网络」提示（设备本地功能照常）。

## 4. 端侧分层：唤醒怎么做

两条路，建议**分期**：

### 阶段一：按键说话（PTT）—— 零额外成本，立即可做

板上有现成的按键（屏上 KEY0 = GPIO40，以及 EC11 的按下）。

- **短按一次** → 进入聆听（脸部变"竖耳朵"）
- 说完静音 1 秒自动结束；**再按一次**可提前结束
- 不需要唤醒词模型，**不占 flash，100% 可靠**

### 阶段二：唤醒词（可选）

用 `esp-sr` 的 **WakeNet**，一个中文唤醒词模型约 **150–250 KB flash**。

- 唤醒词在**设备本地**判定，只有唤醒后才上传音频 → **隐私好、误传少**
- 建议唤醒词：「你好爬爬」（配合昵称）
- ⚠️ 需要在服务端或本地用 ESP-SR 工具训练/选择模型

> 建议：**先把阶段一做好用起来**，唤醒词是锦上添花。桌上的设备，按一下并不麻烦。

## 5. 音频参数（依据实际器件）

### 采集（MSM261S4030H0）

| 项 | 值 | 说明 |
|---|---|---|
| 采样率 | **16 kHz** | ASR 通用标准；文件小 |
| 位深 | 器件是 **24 bit 装在 32 bit 槽** | 固件右移 8 位转成 16 bit |
| 声道 | 单声道（`MIC_LR_GND` 选左声道）| |
| BCLK | 16 k × 32 = **512 kHz** | 落在器件 150–800 kHz 规格内 |
| 灵敏度 / SNR | −26 dBFS @1kHz 1Pa / 57 dB | 桌面 0.5 m 内足够 |

### 播放（MAX98357A）

| 项 | 值 |
|---|---|
| 采样率 | **16 kHz 或 24 kHz**（跟服务端 TTS 输出一致）|
| 位深 | 16 bit |
| 格式 | I2S；**RevB 板上是左对齐**（核丝印已注明）|
| 输出 | BTL，`SPK_P`/`SPK_N` **两端都不接地** |

### ⚠️ 两条硬件红线（设计文档里已写明，实现时不能违反）

1. **MAX98357A 的 `SD_MODE` 禁止直接接 GPIO 或 5V 上拉** —— 会回灌 GPIO。保留模块原配置。
2. **功放 5V 走独立短粗线**，不经 J6 小信号插头（J6 只走音频信号）。

## 6. 服务端协议设计

### 一次请求走完全流程（推荐）

设备只发一次 POST，服务端用**分块流**把中间结果和音频陆续推回来。

```
POST /voice
Content-Type: application/octet-stream
X-Session: <会话 id>

<WAV 字节流：16 kHz / 16 bit / 单声道>
```

响应是**长度前缀的二进制帧**（比 base64 省 33% 带宽，比 SSE 更适合音频）：

```
[1 字节 类型][4 字节 大端长度][载荷]
  1 = JSON 事件    {"type":"asr","text":"今天天气怎么样"}
  2 = JSON 事件    {"type":"token","text":"长沙"}
  3 = PCM 音频块   16k/16bit/mono 裸流
  4 = JSON 事件    {"type":"tool","name":"show_screen","args":{"screen":"weather"}}
  0 = 结束
```

设备侧解析：JSON 事件更新文字/触发动作，PCM 块直接写 I2S。

**为什么不用 SSE**：音频要 base64，多 33% 体积，且设备要额外做解码。
**为什么不用 WebSocket**：ESP32 上要多背一个库，HTTP 分块响应已经够用。

### 服务端内部流水线

```
WAV ──> ASR ──> 文字
                  │
                  ├─ 立刻推 event:asr（设备可以马上显示"你说的是…"）
                  │
                  └─> DeepSeek /chat/completions (stream=true)
                        │
                        ├─ token 流 ──> 攒到句号/问号/换行就切一句
                        │
                        └─> 完整句 ──> TTS ──> PCM ──> 推给设备
```

**关键优化：按句切分**。第一句合成完就发，不等全文。这一条能把首字出声从 8 秒压到 2–3 秒。

## 7. Tool Calls：让语音能操作设备

DeepSeek 支持 Tool Calls，这是**让语音助手真正有用**的关键 —— 否则它只是个聊天框。

建议的工具集：

| 工具 | 参数 | 效果 |
|---|---|---|
| `show_screen` | `screen: face/clock/analog/weather/chatgpt/sys` | 切屏 |
| `set_mood` | `mood: happy/excited/sleepy/sad` | 换表情 |
| `get_weather` | — | 读当前天气（设备已有数据）|
| `get_quota` | — | 读账号额度 |
| `get_time` | — | 读时间 |
| `set_volume` | `level: 0-100` | 音量 |

**执行分工**：服务端解析出 tool call → 作为 `type:4` 事件推给设备 → **设备执行**（因为动作在设备上）→ 设备可以把结果回传，服务端继续生成回答。

**示例对话**：

```
你：看看长沙天气
  → tool: show_screen(weather)
  → 屏幕自动切到天气页
  → 助手：「长沙现在阴，20 度，今天 18 到 25 度。」

你：我额度还剩多少
  → tool: get_quota
  → 助手：「公司 Pro 那个号，七天窗口已经用满了，还剩两张重置券。」
```

> 这就是"桌面助手"和"聊天机器人"的区别。

## 8. UI 联动：把脸用起来

现有的表情屏（160×136 动态区，23 fps）正好承载语音状态：

| 状态 | 表情 | 附加 |
|---|---|---|
| 待机 | 正常呼吸/眨眼 | — |
| **聆听** | 眼睛睁大、向上看 | 底部一条**麦克风电平条**（实时音量）|
| **思考** | 眼睛转向一侧、偶尔眨 | 三个点 `···` 依次亮 |
| **说话** | **嘴跟着音频包络张合** | ← 这个效果最讨喜 |
| 出错 | 难过表情 | 一句短提示 |

**嘴型同步的实现**：播放每个 PCM 块时算它的 RMS，映射到嘴巴张开高度。零额外硬件成本，效果提升巨大。

- 接入完整链路
- **嘴型同步**

## 11. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| **回声** —— 麦克风听到喇叭 | 会自己跟自己对话 | **半双工**：播放时完全不录音。简单有效，先这么做 |
| **CPU 争抢** —— TLS + 音频 + 23fps 刷屏 | 说话时表情掉帧 | I2S 是 DMA（几乎不占 CPU）；TLS 期间本就处于"思考"状态，掉帧可接受 |
| **PSRAM 压力** | 帧缓冲 150KB + 音频缓冲 | PSRAM 有 8 MB，充裕；音频缓冲放 PSRAM |
| **功放电流尖峰** | 可能拉低电源导致复位 | 电池标称 ≥10A；功放 5V 走独立短粗线（PCB 已如此设计）|
| **断网** | 功能不可用 | 降级为本地六屏 + 提示；不崩 |
| **ASR 识别错** | 答非所问 | 把 ASR 文字**显示在屏幕上**，你能立刻看出是听错了还是理解错了 |
| **flash 不够** | 装不下唤醒词 | 当前剩 1.9 MB，WakeNet 只占 ~200 KB，够 |
