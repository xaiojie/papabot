## 二、架构

```
ESP32（家里）              papa.papaclaoud.top              手机/电脑
     │                            │                            │
     │  WSS /ws/device?key=…      │   WSS /ws/client?token=…   │
     ├───────────────────────────→│←───────────────────────────┤
     │      （设备固定密钥）        │      （账号密码换 token）   │
     │                            │                            │
     │←──── 命令转发 ──────────────┼────────────────────────────┤
     │───── 画面帧（二进制）───────┼───────────────────────────→│
```

**关键点：ESP32 是主动「出站」连接** —— 不需要公网 IP、不需要端口映射。

### 分层

| 层 | 组件 | 位置 |
|---|---|---|
| TLS 终止 + 静态页 | nginx 1.20.1 | 宿主 `/etc/nginx/conf.d/papa.conf` |
| 前端 | 单页 HTML（13.7 KB）| 宿主 `/var/www/papa/index.html` |
| WebSocket 中转 + API | Node.js 20 容器 | `127.0.0.1:8790` |
| 证书 | Let's Encrypt（ecdsa）| `/etc/letsencrypt/live/papa.papaclaoud.top/` |

## 三、接口

### HTTP

| 方法 | 路径 | 认证 | 说明 |
|---|---|---|---|
| GET | `/api/health` | 无 | 健康检查（给 uptime-kuma 用）|
| POST | `/api/login` | 账号密码 | 返回 token |
| GET | `/api/status?token=` | token | 设备在线状态 |

### WebSocket

| 路径 | 认证 | 用途 |
|---|---|---|
| `/ws/device?key=<设备密钥>` | 设备密钥 | ESP32 接入 |
| `/ws/client?token=<token>` | token | 浏览器接入 |

### 消息协议

**文本帧 = JSON**

```jsonc
// 浏览器 → 服务器 → 设备
{ "type": "cmd", "id": "c1", "cmd": "next" }

// 设备 → 服务器 → 浏览器
{ "type": "status", "screen": "clock", "heap": 123456 }
{ "type": "hello",  "info": { "fw": "1.0", "chip": "esp32s3" } }
```

**二进制帧 = 原样透传**（画面数据，服务器不解码）

> 约定：第 1 字节为帧类型，`1` = RLE RGB565 帧（**待与固件对齐后实现**）

**安全设计**：
- 服务器只转发 `type === "cmd"` 的浏览器消息，不透传任意内容
- 设备密钥和 token 都用 `timingSafeEqual` 常量时间比较
- token 是 HMAC 签名的无状态令牌，默认 7 天有效期

## 八、踩过的两个坑

### ① 容器内不能绑 127.0.0.1

```js
server.listen(PORT, '127.0.0.1')   // ❌ docker-proxy 从桥接网段来，到不了容器 loopback
server.listen(PORT, '0.0.0.0')     // ✅
```

**现象**：宿主 `curl 127.0.0.1:8790` 返回 000，nginx 返回 502。
**安全性不受影响** —— docker 端口发布仍只绑宿主 `127.0.0.1`，外面还有 nginx。

### ② Dockerfile 里 `USER node` 前必须 chown

```dockerfile
COPY server.js ./
RUN chown -R node:node /app     # ← 不写这行，node 用户读不了 root 的文件
USER node
```

**现象**：容器无限重启，日志 `EACCES: permission denied, open '/app/server.js'`

**① 复用现有命令分发器 —— 串口和云端走同一条路**

```cpp
static void cloudCommandBridge(const char *line) {
```

## 十四、画面预览（2026-09-11 完成）

网页上实时看到设备屏幕。

### 数据流

```
ESP32 PSRAM 帧缓冲 (320×240 RGB565)
   ↓ RLE 编码（固件 cloud::sendFrameRLE）
   ↓ 二进制 WebSocket 帧
中转服务（原样透传，不解码）
   ↓
浏览器解码 → canvas 显示（前端 onFrame）
```

### 帧格式（二进制，小端）

```
byte 0      : 0x01       帧类型 = RLE 全帧
byte 1..2   : width      uint16
byte 3..4   : height     uint16
byte 5..6   : runCount   uint16
之后 runCount 组，每组 4 字节：
  byte 0..1 : count    uint16（同色连续像素数，行优先线性扫描）
  byte 2..3 : RGB565   uint16
```

**为什么不用串口那套文本格式**：

| | 文本（dumpr）| 二进制（新）|
|---|---|---|
| 每 run | 9 个 ASCII 字符 | **4 字节** |
| 解码 | 字符串解析 | 直接读 uint16 |
| 实测全帧 | ~6.8 KB | **3.0–3.3 KB** |

### 实测数据

```
首帧像素校验   76800 vs 期望 76800   ✅（RLE 编码正确）
平均帧大小     3198 字节
平均 run 数    798
压缩比         48x（153600 → 3198）
实际帧率       4.5 fps（上限设 5）
带宽           116 kbps（服务器上行 18.6 Mbps，余量 160 倍）
```

**颜色校验**（与 `config.h` 逐项对照）：

| 帧里的 RGB565 | 解出的 RGB | config.h 定义 | |
|---|---|---|---|
| `0x6ebd` | rgb(106,214,238) | `C_EYE` = rgb565(0x6a,0xd4,0xe8) | ✅ |
| `0x8f1e` | rgb(139,226,246) | `C_EYE_SOFT` = rgb565(0x8f,0xe3,0xf2) | ✅ |
| `0x0000` | rgb(0,0,0) | `C_BG` 黑 | ✅ |

### 新增命令

```
cloud stream on [fps]    开始推流（fps 夹在 1..20，默认 5）
cloud stream off         停止
cloud stream             查看状态
```

**省流设计**：
- 只在画面有脏矩形时编码；**但即使静止也每 3 秒补一帧** ——
  否则新打开的网页要等到下次画面变化才看得到东西
- 输出缓冲放 **PSRAM**（16 KB），不占内部堆
- 缓冲不够时**丢弃整帧**而不是发半帧（避免浏览器画出残缺画面）

### 前端

- `onFrame()` 解码 RLE → RGB565 转 RGB888 → 写 `ImageData`
- 用 **`Uint32Array` 视图**逐像素写入（比逐字节快得多）
- `image-rendering: pixelated` 保持像素锐利
- 进控制台自动开流（5 fps）

### 🐛 验证时踩的坑（不是固件问题）

写 Node 验证脚本时用了 `new Uint8Array(w*h)` 存 RGB565，
**16 位颜色被截断成低 8 位** —— `0x6EBD` 变成 `0xBD`，
画出来是蓝色而不是青色，一度以为是固件编码错了。

**改用 `Uint16Array` 后颜色完全正确。**
（前端本来就用 `Uint32Array`，没这个问题。）

**教训**：验证脚本本身也会骗人 —— 颜色不对时先怀疑自己的解码，
再用「和固件里的常量逐项对拍」来确认。

## 十五、修掉的两个 bug（2026-09-11）

### 🐛 BUG 1：快速点屏幕按钮会跳回「表情」

**现象**：网页上点屏，间隔短的时候会自动跳到 face。

**根因**（固件）：
```cpp
const int n = atoi(w1);                     // atoi("dial") = 0
if (n >= 0 && n < apps::screenCount()) gotoScreen(n);   // 0 在范围内 → 通过！
```
屏名匹配不上时走 `atoi` 兜底，**而 `atoi` 对非数字返回 0，0 恰好是 face** ——
守卫只查了范围，拦不住。

**触发条件**：网页上写了两个错的屏名
```
data-cmd="screen dial"    ← 固件里叫 analog
data-cmd="screen quota"   ← 固件里叫 chatgpt
```

**修复**：
```cpp
char *endp = nullptr;
const long n = strtol(w1, &endp, 10);
if (endp && *endp == '\0' && endp != w1 && n >= 0 && n < apps::screenCount()) {
  gotoScreen(static_cast<int>(n)); return;
}
// 否则报错并列出可用屏名，不再默默跳到第 0 屏
```
**必须是纯数字才当序号用。** 同时修正了网页上的两个错名。

### 🐛 BUG 2：「不跟手」

**现象**：点按钮后要等一会儿才亮。

**根因**：高亮只由设备上报的状态驱动，一个来回 200~500 ms。

**修复**：**乐观高亮** —— 点下去立刻亮，设备回执再校准。
```js
if (cmd.startsWith('screen ')) markScreen(cmd.slice(7));   // 先亮
send(cmd);
```

### 🐛 BUG 3：浏览器缓存旧页面

**现象**：改了前端但手机上还是旧的，表现成「点了没反应 / 跳错屏」。

**修复**：nginx 加 `Cache-Control: no-cache, must-revalidate`。

## 十七、修掉「画面只显示一帧不动」（2026-09-11）

**用户反馈**：网页上画面始终停在同一个表情，不实时。

### 排查

```json
服务器: { "deviceOnline": true, "clients": 2 }
抓帧:   8 秒收到 0 帧
```

**设备在线、浏览器连着，但一帧都没有** —— 推流是关的。

### 根因：设计缺陷，不是偶发故障

推流默认是 **关** 的，只能靠手动 `cloud stream on` 打开。问题是：

- 我在上一轮测试结束时发了 `cloud stream off` → 一直关着
- **设备重启后也是关的**
- **浏览器重连后设备不知道有人要看**

**最关键的是：服务器从来没告诉过设备「有几个浏览器在看」。**
所以设备无从判断该不该推流。

### 修复（三层）

**① 中转服务告诉设备浏览器数量**（`server.js`）

```js
function notifyDeviceClients() {
  if (!deviceOnline()) return;
  device.ws.send(JSON.stringify({ type: 'clients', count: clients.size }));
}
// 浏览器上线 / 下线时各调一次
```

**② 设备据此自动开关推流**（`cloud.cpp`）

```cpp
} else if (!strcmp(t, "clients")) {
  const int n = doc["count"] | 0;
  s_clientCount = n;
  if (n > 0 && !s_streaming)      setStreaming(true, s_streamFps);
  else if (n == 0 && s_streaming) setStreaming(false);
}
```

**没人看就不推** —— 省带宽和 CPU；有人看就自动开始，不用手动干预。

**③ 前端看门狗兜底**（`index.html`）

```js
// 15 秒没收到帧就重新请求一次
setInterval(() => {
  if (!ws || ws.readyState !== 1) return;
  if (lastFrameAt && Date.now() - lastFrameAt > 15000) {
    send('cloud stream on 5');
    lastFrameAt = Date.now();
  }
}, 10000);
```

覆盖设备重启、网页从后台回来、上次会话关了流等情况。


### 教训

**推流开关不能只靠手动命令。** 一个「可选开关」如果没有明确的触发方，
就一定会出现「有人看但没人开」的状态 —— 而用户看到的是「坏了」。

**正确的模型**：让**需求方**（浏览器）的存在本身成为触发信号，
服务器做中转，设备据此决策。

## 十八、额度刷新改成 5 分钟（2026-09-11）

**用户反馈**：额度变了但屏幕还是旧值，每次都要手动按太麻烦。

### 原有机制

```cpp
QUOTA_REFRESH_MS = 10u * 60u * 1000u;   // 10 分钟
```

**数据其实一直在后台更新**，只是：
- 周期长（10 分钟）
- 而且**只有正看着额度屏时才重绘**
  ```cpp
  if (currentApp == Id::Weather || currentApp == Id::ChatGpt) gotoScreen(gScreen);
  ```
- 失败会 1 分钟后重试（`NET_RETRY_MS`）

### 改动

```cpp
// 2026-09-11：10 分钟 → 5 分钟。额度变化比天气频繁，10 分钟太钝；
// 5 分钟 = 每天 288 次请求，对自建 sub2api 完全没压力。
constexpr uint32_t QUOTA_REFRESH_MS = 5u * 60u * 1000u;
```

天气仍是 20 分钟（和风免费版有日调用上限）。

### 实测验证（串口监控 7 分钟）

```
[+  14.2s] weather/quota: HTTP 200  →  quota OK: primary=0% …
[+ 318.2s] weather/quota: HTTP 200  →  quota OK: primary=0% …

间隔 = 304 秒 = 5.07 分钟   ✅
```

### 顺带确认：数据链路是通的

设备拉到的值和屏幕显示的值一致：

| | 值 |
|---|---|
| 设备日志 | `公司Pro(id=2839) active primary=0%/10080min reset=09-19 16:20 credits=2` |
| 屏幕截图 | `公司Pro / 已限流 / 7天 0% / 重置 09-19 16:20 / 重置券 2 张` |

**说明「不更新」不是取数失败，只是触发周期太长。**

### 网页上仍保留「立刻刷」入口

```
[换表情] [刷新额度] [刷新天气] [性能]
```

对应固件的 `quota` / `weather` 命令（拉取后强制重绘）。
