# 网页控制台 · 规划方案

2026-09-11。**一个网页能实现哪些功能，怎么做，有哪些坑。**

---

## 〇、先说结论：三条路，推荐第三条

| 方案 | 全平台 | 需要 HTTPS | 带宽 | 复杂度 | 评价 |
|---|---|---|---|---|---|
| **A. 纯 BLE 网页**（Web Bluetooth）| ❌ **iOS 不支持** | ✅ 需要 | 低（~25KB/s）| 中 | ⚠️ 只适合安卓 |
| **B. 纯 WiFi 网页**（ESP32 自建服务器）| ✅ | ❌ 不需要 | **高** | **低** | ✅ |
| **C. WiFi 为主 + BLE 为辅**（推荐）| ✅ | 部分 | 高 | 中 | ✅ **最佳** |

### 🎯 核心判断

**ESP32 自己当 Web Server 是更优解**，理由：

```
✅ iOS / 安卓 / 电脑 全平台通用
✅ 局域网内 http://192.168.x.x —— 不需要 HTTPS 证书
✅ 带宽够（WiFi 实测能跑 17.8fps 画面预览，BLE 只有 3fps）
✅ 不依赖外网
✅ 网页资源可以放 PSRAM（我们有 8MB）
```

**BLE 的价值只剩一个**：不想切 WiFi 时配网。但代价是「iOS 用不了 + 必须 HTTPS 托管」—— **不划算**。

**→ 配网改用 AP 模式（设备自己当热点），全平台通用，不需要 HTTPS。**

## 二、技术架构

### 设备端（ESP32-S3）

```
┌─────────────────────────────────────────────┐
│  启动                                        │
│    ↓                                         │
│  有线凭据吗？──否──→ AP 模式                 │
│    │                  SSID: 爬爬-配网         │
│   是                  网页: 192.168.4.1      │
│    ↓                  ↓                      │
│  连 WiFi ←────── 用户配网 ────┘              │
│    ↓                                         │
│  STA 模式 + mDNS (爬爬.local)                │
│    ↓                                         │
│  Web Server                                  │
│    ├─ HTTP  静态页面（gzip，放 flash/PSRAM） │
│    ├─ HTTP  REST API（/api/status 等）       │
│    ├─ WS    命令通道（复用命令分发器）        │
│    ├─ WS    画面流（RLE 帧）                  │
│    └─ HTTP  OTA 上传                          │
└─────────────────────────────────────────────┘
```

### 复用现有资产（重要）

**你已经有的、可以直接复用的：**

| 现有资产 | 复用方式 |
|---|---|
| **串口命令分发器**（`next`/`prev`/`mood`/`pulse`/`set nick`…）| **WS 收到的字符串直接喂给它** —— 几乎零改动 |
| **RLE 帧编码**（实测 6.8KB/帧、17.8fps）| 把串口的输出改道到 WebSocket |
| **`docs_server.py` 的实时取景服务** | 逻辑已经在，改成设备端自建 |
| **`canvas.cpp` 帧缓冲 + 脏矩形** | 直接复用，预览就是读帧缓冲 |
| **`Preferences`(NVS) 持久化** | 网页设置写 NVS |

**→ 这个架构的最大好处：固件改动很小，主要是「加一个 Web Server + 把串口输出改道到 WS」。**

### 前端

```
单页应用（SPA），纯静态
  ├─ index.html
  ├─ app.js        （原生 JS 或轻框架）
  ├─ style.css
  └─ 打包后 gzip，预计 30-60 KB

通信：
  ├─ REST   /api/status, /api/settings, /api/wifi/scan
  ├─ WS     /ws/cmd    命令通道（文本）
  └─ WS     /ws/frame  画面流（二进制）
```

**前端体积要控制**：ESP32 的 flash 有 42% 余量，但网页 + 字库 + 固件加起来要算总账。
**建议 50KB 以内**，必要时放 PSRAM 或 SPIFFS/LittleFS 分区。

## 三、要不要保留 BLE？

**建议：保留 BLE，但定位降到「安卓用户的便捷配网」**

| 场景 | 用哪个 |
|---|---|
| **配网（主）** | AP 模式 —— 全平台 |
| 配网（备选）| BLE —— 仅安卓，且需要 HTTPS 托管的页面 |
| 日常控制 | **WiFi 网页**（唯一选择，因为带宽）|
| 低功耗远程 | BLE —— 但我们是插电设备，不需要 |

**→ 如果嫌麻烦，BLE 可以整个不做。** 省下约 50KB flash + 40KB RAM。

## 五、技术约束与坑

### 🔴 必须知道的

| # | 约束 | 影响 |
|---|---|---|
| 1 | **Web Bluetooth 不支持 iOS** | 想用 BLE 就必须放弃 iPhone 用户 |
| 2 | **Web Bluetooth 必须 HTTPS** | 页面不能放设备上（设备只有 http）|
| 3 | **HTTPS 页面不能请求 http:// 设备**（Mixed Content）| 所以「HTTPS 页面 + HTTP 设备」这条路是死的 |
| 4 | **BLE 实吞吐 ~25KB/s** | 画面预览只能 3fps，**必须走 WiFi** |

### 🟡 要注意的

| # | 事项 | 说明 |
|---|---|---|
| 5 | **AP 配网时手机可能提示"无互联网"** | 正常，继续用即可（iOS 可能要手动关「无线局域网助理」）|
| 6 | **WiFi + BLE 共存有性能折损** | 若两个都开，画面帧率会降 |
| 7 | **`ARDUINO_LOOP_STACK_SIZE=16384`** | 已为 TLS 提过栈，Web Server 也可能吃栈 |
| 8 | **网页资源体积** | 建议 ≤50KB，否则要挤 flash |
| 9 | **凭据安全** | sub2api admin Key 权限很高，网页写入要提示风险 |
| 10 | **OTA 掉电变砖** | 建议双分区 OTA（`default_8MB.csv` 要确认够）|

### 🟢 可以放心的

- ESP32-S3 跑 Web Server + WS 很轻松（RAM 才用 22.3%）
- 画面预览带宽：WiFi 局域网 >1MB/s，17.8fps 的 6.8KB 帧只占 120KB/s，**余量很大**
- 8MB PSRAM 基本空闲，网页可以放进去

## 六、一句话总结

> **做一个「ESP32 自己托管的网页」——手机连上设备就能：配网、看屏幕实时画面、切屏、控舵机、改设置、升级固件。**
>
> **不需要 BLE，不需要 HTTPS，iOS 安卓都能用。**

**如果一定要 BLE**（比如你主要用安卓、且不想切 WiFi），那就在这个基础上**再加一个独立的 HTTPS 配网页**，其余功能仍走 WiFi 网页。
